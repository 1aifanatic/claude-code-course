Path 1 · OperateModule 0430 minStable

Implement through bounded feedback loops

Keep each change small enough to inspect, test, redirect, and recover.

PLAIN-LANGUAGE DEFINITION

Bounded implementation divides a change into reversible increments, each with a narrow purpose and an immediate feedback signal.

Learn→Demonstration→Guided lab→Transfer→Evidence→Quiz
BY THE END

You will be able to—

  1. 01Choose an appropriate implementation slice
  2. 02Use tests and diffs as continuous feedback
  3. 03Course-correct without compounding a failed approach
KEY TERMS

Words to use precisely

Vertical slice
A small end-to-end piece of behavior crossing only the layers needed to demonstrate value.
Feedback loop
The time between making a change and observing evidence about it.
Rewind
Restoring conversation or code state to an earlier checkpoint when an approach should be abandoned.
Open the complete glossary →
01
Execution

Ask for one observable increment, not the entire epic

A bounded slice might add a domain rule and its unit tests before touching HTTP or UI. Another slice might preserve the API contract while swapping an internal implementation. The best boundary makes failure easy to localize.

Review the diff after each slice. If Claude modified unrelated files, stop and ask why before proceeding. Small diffs expose mistaken assumptions while they are cheap to reverse.

  • State the files or behavior in scope.
  • Define what remains out of scope.
  • Run the narrowest meaningful check.
  • Summarize evidence before continuing.
02
Correction

Use interruption and rewind as engineering tools

When the approach is wrong, a long apologetic conversation rarely cleans the context. Stop the run, identify the incorrect assumption, and decide whether a short correction is enough.

If repeated corrections accumulate or the code state is no longer trustworthy, restore a known checkpoint or begin a clean session from the spec and current diff.

  • Interrupt at the first material divergence.
  • Never ask Claude to hide or rationalize unexpected changes.
  • Keep a recoverable Git checkpoint before risky refactors.
  • Prefer new evidence over repeated persuasion.
Example
git status --short
git diff --stat
git diff
npm test -- --test-name-pattern=transition

PRACTICAL FRAMEWORK

Slice → inspect → prove

Every implementation increment should pass through four gates.

  1. 01
    Slice

    Choose one behavior or internal contract.

  2. 02
    Change

    Make only the edits needed for that slice.

  3. 03
    Inspect

    Read the complete diff and unexpected file list.

  4. 04
    Prove

    Run a focused check, then the broader relevant suite.

  5. 05
    Commit or recover

    Create a checkpoint when evidence is good; rewind when it is not.

The slice has a crisp boundary, direct evidence, and a deliberate pause before dependent layers.

GUIDED RELAYBOARD LAB

Implement the domain slice

15–25 min

Scenario

Add the resolution transition to RelayBoard’s domain service without changing HTTP or UI code.

Useful command
npm test -- --test-name-pattern=resolution

Work sequence

  1. Create a recoverable Git checkpoint.
  2. Ask Claude to implement only the domain rule and unit tests.
  3. Inspect git status and the complete diff.
  4. Run the focused test, then stop even if Claude offers to continue.

Record the checkpoint only if the diff stays within the agreed slice and the focused tests demonstrate both allowed and rejected behavior.

COMMON FAILURE MODES

Watch for these

  • Combining a feature, refactor, dependency upgrade, and formatting pass
  • Allowing unrelated cleanup without reviewing its risk
  • Continuing after the plan’s assumptions are disproved
SAFETY + VERIFICATION

Pause before proceeding

Never use broad undo or cleanup commands until you have identified which changes belong to the learner and which may predate the session.

ONE-SENTENCE TAKEAWAY

Short feedback loops turn Claude’s speed into controllable progress instead of fast-moving uncertainty.
