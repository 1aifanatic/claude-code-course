Engineer effective CLAUDE.md, rules, and memory

Put durable guidance where it loads reliably without drowning the task.

PLAIN-LANGUAGE DEFINITION

Project instructions are versioned, scoped context that tells Claude how this repository is built, tested, structured, and governed; memory records learned details that may persist across sessions.

Learn→Demonstration→Guided lab→Transfer→Evidence→Quiz

  2. 02Write concise instructions that can be verified

KEY TERMS

Words to use precisely

CLAUDE.md
A Markdown file loaded as persistent instructions at project, user, or managed scope.
Path-scoped rule
A rule under .claude/rules that loads when Claude works with matching paths.
Auto memory
Claude-maintained notes about repository learnings, stored separately from versioned project instructions.

01
Placement

Always-on context should earn its rent

Root CLAUDE.md is for facts and rules needed in nearly every session: canonical build commands, core architecture, important invariants, and non-negotiable workflow requirements. Keep it concise; official guidance recommends targeting under 200 lines.

Move file-type or subsystem guidance to path-scoped rules. Move multi-step procedures and large references to skills. Personal machine details belong in local or user scope, not the shared repository file.

  • Prefer exact commands over ‘run the tests.’
  • Explain unusual architecture, not what the code makes obvious.
  • Write enforceable wording for safety-critical rules.
  • Delete stale guidance when the repository changes.
02
Validation

Instructions are context, not enforcement

Claude may interpret conflicting or vague instructions differently. Use /context and /memory to confirm what loaded, /doctor to catch configuration problems, and hooks or CI when a rule must be deterministic.

Treat auto memory as inspectable working notes. Correct or delete stale entries; do not assume machine-local memory is shared team knowledge.

  • Check source and scope of every instruction.
  • Look for contradictions between user, project, nested, and managed guidance.
  • Measure whether a rule changes behavior in realistic tasks.
  • Promote repeated, validated knowledge into versioned project artifacts.

PRACTICAL FRAMEWORK

The LOAD decision

Choose the layer based on frequency, scope, and enforcement need.

  1. 01
    Every session

    Root CLAUDE.md for concise universal context.

  2. 02
    Matching paths

    .claude/rules for subsystem or file-type guidance.

  3. 03
    Specific task

    Skill for an on-demand procedure or reference.

  4. 04
    Discovered locally

    Auto memory for inspectable learned notes.

  5. 05
    Must enforce

    Hook, permission, sandbox, test, or managed policy—not prose alone.

ANNOTATED DEMONSTRATION

Weak instruction, stronger contract

Under-specified

Write clean code. Always follow best practices. Test everything.

Bounded and checkable

Build: npm run build. Focused tests: npm test -- --test-name-pattern=<name>. Domain code under src/domain must not import src/http. Preserve the IncidentError public code values. Before completion, run npm test and git diff --check; report commands and exit status.

WHY IT WORKS

Specific commands, boundaries, and contracts are more actionable and verifiable than generic quality language.

COMMON FAILURE MODES

Watch for these

  • Copying the README into CLAUDE.md
  • Using vague preferences that cannot be checked
  • Treating instructions as security enforcement
SAFETY + VERIFICATION

Pause before proceeding

Never commit local tokens, personal paths, internal endpoints, or sensitive examples into shared instructions. Use placeholders and approved secret mechanisms.

ONE-SENTENCE TAKEAWAY

Persistent context should be concise, scoped, current, and backed by enforcement when consequences demand it.
