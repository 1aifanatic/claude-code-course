Verify, debug, review, and recover

Turn claims of completion into evidence that could prove the work wrong.

PLAIN-LANGUAGE DEFINITION

Verification deliberately seeks observations that discriminate between a correct change and plausible-looking failure; debugging forms and tests competing explanations for observed defects.

Learn→Demonstration→Guided lab→Transfer→Evidence→Quiz
BY THE END

You will be able to—

  1. 01Build a layered verification strategy
  2. 02Diagnose from evidence rather than edit by intuition
  3. 03Review diffs for correctness, scope, security, and maintainability
KEY TERMS

Words to use precisely

Red-capable test
A check known to fail when the target defect or missing behavior is present.
Hypothesis
A falsifiable explanation that predicts an observable result.
Regression
Previously working behavior broken by a change.

01
Verification

A green command is meaningful only when it can catch the failure

Claude can run a test command that exits successfully while never exercising the changed behavior. Ask what the test proves, whether it failed before the fix, and what important layer remains unobserved.

Layer evidence: focused unit tests for the rule, integration tests for boundaries, static checks for types, manual checks for user-visible behavior, and diff review for unintended scope.

  • Capture the failing baseline when feasible.
  • Use positive, negative, boundary, and authorization cases.
  • Run the broader impacted suite after the focused check.
  • Separate observed evidence from confidence language.
02
Debugging

Change one belief at a time

A scientific debug loop starts from the symptom, gathers a minimal reproduction, lists plausible causes, and runs the cheapest discriminating experiment. Editing before the hypothesis predicts a result creates noisy motion.

Ask Claude to keep a hypothesis table with supporting evidence, contradicting evidence, and the next test. When a hypothesis fails, retire it rather than layering more patches on top.

  • Reproduce reliably.
  • Localize the failing boundary.
  • Generate competing explanations.
  • Run one discriminating experiment.
  • Add a regression test before declaring victory.
Example
npm test
npm run typecheck
git diff --check
git diff

PRACTICAL FRAMEWORK

The EVIDENCE stack

Do not let one green signal carry more meaning than it earned.

  1. 01
    Reproduction

    Can the original failure be observed?

  2. 02
    Focused test

    Does a red-capable check prove the target behavior?

  3. 03
    Boundary test

    Do interfaces, persistence, and errors still agree?

  4. 04
    Broad suite

    Did related behavior regress?

  5. 05
    Human review

    Does the diff match the intended scope and risk?

ANNOTATED DEMONSTRATION

Weak instruction, stronger contract

Under-specified

Tests pass, so the incident fix is done.

Bounded and checkable

The new invalid-transition test failed against the starter and passes after the domain fix. All 18 unit tests and TypeScript checks pass. Manual API inspection confirms the existing 409 error shape. The diff changes one service and one test file; no persistence or UI contract changed.

WHY IT WORKS

The evidence states what was tested, its red capability, the broader check, the manual boundary, and the mutation scope.

TRY IT IN CLAUDE CODE

A reusable starting request

Adapt bracketed material to approved project information. Review proposed actions before granting authority.

Verify this change adversarially. First state the claims the implementation makes. For each claim, identify a test or inspection that could disprove it. Reproduce the prior failure where possible, run focused and broader checks, inspect the complete diff, and report observed evidence separately from remaining uncertainty.

GUIDED RELAYBOARD LAB

Catch the stale-version defect

25–35 min

Scenario

RelayBoard’s update path can overwrite a newer incident because it ignores the expected version.

Useful command
npm test -- --test-name-pattern=version

Work sequence

  1. Run the concurrency-focused test and capture the failure.
  2. Ask Claude for at least three hypotheses before editing.
  3. Run the cheapest experiment that distinguishes the leading hypotheses.
  4. Implement the minimal fix and add a regression test that fails against the starter.

Record this checkpoint only when the regression test is demonstrably red-capable and the full suite passes after the fix.

COMMON FAILURE MODES

Watch for these

  • Using the implementation’s own explanation as verification
  • Running only a broad suite that never covers the new behavior
  • Making several speculative edits before rerunning the reproduction
SAFETY + VERIFICATION

Pause before proceeding

Debug output can expose tokens, personal data, or proprietary payloads. Redact evidence before placing it in prompts, logs, screenshots, or the Evidence Log.

ONE-SENTENCE TAKEAWAY

Verification is strongest when it was designed to make an incorrect implementation fail visibly.
