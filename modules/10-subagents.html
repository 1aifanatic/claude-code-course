Design and control subagents

Delegate focused work to isolated contexts without giving away coordination or judgment.

PLAIN-LANGUAGE DEFINITION

A subagent is a specialized worker with its own context, instructions, tool access, and optional model that performs a bounded task and returns a result to the parent session.

Learn→Demonstration→Guided lab→Transfer→Evidence→Quiz
BY THE END

You will be able to—

  1. 01Choose delegation for context isolation or specialization
  2. 02Write a bounded subagent contract
  3. 03Control tools, permissions, background behavior, and output
KEY TERMS

Words to use precisely

Context isolation
Performing work in a separate context so detailed exploration does not occupy the parent conversation.
Tool allowlist
The specific tools a subagent is permitted to use.
Background subagent
A concurrent worker that cannot pause for new permission approvals and may therefore auto-deny blocked actions.
Open the complete glossary →
01
Delegation

Delegate a result, not a vague role

Subagents are valuable when a side task would flood the main context, when a specialist needs a narrow tool set, or when independent review benefits from fresh context. They are not a reason to fragment tightly coupled work.

The parent should specify the objective, evidence sources, authority, output schema, stopping condition, and relationship to other work. A ‘security expert’ role without a concrete review target is not a task contract.

  • Give one bounded objective.
  • Provide only necessary tools and skills.
  • Require path-level evidence.
  • Return a concise result that the parent can integrate.
02
Concurrency

Parallelism helps only when ownership is separable

Background subagents can perform independent research while the parent continues, but they cannot resolve interactive permission questions. Design their work as read-only where possible.

Subagents do not automatically coordinate with one another. The parent remains responsible for task partitioning, resolving contradictions, and preventing simultaneous edits to the same files.

  • Use foreground mode for permission-sensitive work.
  • Use background mode for independent, pre-authorized research.
  • Assign file or concern ownership before parallel edits.
  • Compare findings rather than accepting the first report.
Example
---
name: test-investigator
description: Investigate a failing RelayBoard test and return evidence. Use for reproducible test failures.
tools: Read, Grep, Glob, Bash
permissionMode: plan
---
Reproduce the named failure, form competing hypotheses, and return evidence. Do not edit files.

PRACTICAL FRAMEWORK

The DELEGATE brief

A worker should be able to finish without silently expanding scope.

  1. 01
    Deliverable

    What exact result must return?

  2. 02
    Evidence

    Which files, commands, and observations support it?

  3. 03
    Limits

    Which tools, paths, actions, and assumptions are excluded?

  4. 04
    Exit

    When is the task complete or blocked?

  5. 05
    Glue

    How will the parent reconcile the result with the main task?

ANNOTATED DEMONSTRATION

Weak instruction, stronger contract

Under-specified

Have several agents improve the project.

Bounded and checkable

Use a read-only test-investigator subagent to reproduce the stale-version failure, inspect only the domain service, repository, and focused tests, and return a hypothesis table with path-level evidence. Do not edit. Stop when one hypothesis is supported by a discriminating test or when the reproduction is not stable.

WHY IT WORKS

The subagent has a result, evidence scope, tool boundary, and stopping rule.

A reusable starting request

Adapt bracketed material to approved project information. Review proposed actions before granting authority.

Decide whether this side task should stay in the main session, use a subagent, or use a separate worktree/session. Explain the context, coupling, permission, edit-collision, and communication tradeoffs. If delegation fits, write a DELEGATE brief and the narrowest subagent configuration.

GUIDED RELAYBOARD LAB

Create the test-investigator

25–35 min

Scenario

Build a read-only subagent that investigates RelayBoard failures without editing code.

Useful command
@test-investigator investigate the failing version-conflict test

Work sequence

  1. Create .claude/agents/test-investigator.md with a clear matching description.
  2. Restrict tools and use plan permission mode.
  3. Give it the stale-version or audit-log failure.
  4. Compare its returned hypothesis table with your own direct inspection.

Record this checkpoint when the subagent returns reproducible evidence, makes no edits, and the parent can decide the next action from its summary.

COMMON FAILURE MODES

Watch for these

  • Delegating tasks that share the same files without ownership
  • Giving a reviewer edit tools it does not need
  • Assuming background workers can ask for new permissions
SAFETY + VERIFICATION

Pause before proceeding

A subagent’s isolation does not erase its authority. Review inherited permissions, MCP access, preloaded skills, and background limitations before use.

ONE-SENTENCE TAKEAWAY

Good delegation isolates context and authority around a result the parent knows how to judge.
