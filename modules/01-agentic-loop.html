How Claude Code actually works

Replace magical thinking with a controllable model of observe, decide, act, and verify.

PLAIN-LANGUAGE DEFINITION

Claude Code is an agentic coding environment: a model reasons over your request and available context, chooses tools, observes their results, and repeats until it reaches a stopping condition or needs your decision.

Learn→Demonstration→Guided lab→Transfer→Evidence→Quiz
BY THE END

You will be able to—

  1. 01Trace the agentic loop from request to evidence
  2. 02Separate model reasoning from tool authority
  3. 03Recognize when to intervene, stop, or narrow the task
KEY TERMS

Words to use precisely

Agentic loop
A repeating cycle of interpreting the goal, choosing an action, observing the result, and deciding what to do next.
Tool
A bounded capability such as reading a file, editing code, running a command, or calling an external service.
Permission
A control that determines whether a tool action is allowed, denied, or requires approval.

01
Mental model

Claude does not see your repository all at once

A session begins with instructions and selected context, not a perfect model of the codebase. Claude gathers evidence through file search, reads, command output, and connected tools. Every observation consumes attention; irrelevant output competes with the task.

The useful unit is therefore not the prompt alone. It is the complete loop: your goal, the context Claude discovers, the actions it is allowed to take, the feedback it receives, and the evidence used to stop.

  • A fluent explanation is not proof that the right file was inspected.
  • An edit is not complete until the relevant behavior is checked.
  • A permission prompt is a decision boundary, not an interruption to dismiss automatically.
02
Control

Your job moves from typing code to shaping the loop

Strong operators define observable success, expose authoritative commands, and keep changes reversible. They inspect the plan when uncertainty is high and the diff when execution is complete.

Intervene early when Claude is solving the wrong problem. A short correction preserves more time and context than letting an incorrect approach grow.

  • Frame the work unit.
  • Make the important evidence discoverable.
  • Bound authority and blast radius.
  • Require a verification signal before completion.

PRACTICAL FRAMEWORK

The OODA-V loop

Use this five-part loop to inspect any Claude Code task.

  1. 01
    Observe

    What repo state, instructions, tests, and constraints did Claude actually read?

  2. 02
    Orient

    What model of the task and architecture is it using?

  3. 03
    Decide

    What plan, tradeoff, or tool choice follows from that model?

  4. 04
    Act

    What bounded edit or command is being performed?

  5. 05
    Verify

    What evidence shows the intended behavior changed without unacceptable damage?

ANNOTATED DEMONSTRATION

Weak instruction, stronger contract

Under-specified

Fix the incident endpoint.

Bounded and checkable

Investigate why PATCH /incidents/:id accepts an invalid status. First identify the transition rules and relevant tests. Propose the smallest fix, then implement it and run the focused tests. Do not change public response shapes. Report the root cause, diff summary, and test evidence.

WHY IT WORKS

The stronger request does not micromanage implementation. It supplies boundaries, an evidence path, and a stopping contract.

TRY IT IN CLAUDE CODE

A reusable starting request

Adapt bracketed material to approved project information. Review proposed actions before granting authority.

Before changing anything, explain your current model of this task as: goal, relevant context discovered, assumptions, proposed actions, permission-sensitive actions, verification evidence, and stop conditions. Ask only questions that materially change the approach.

GUIDED RELAYBOARD LAB

Observe the loop on RelayBoard

15–25 min

Scenario

Start Claude Code in the RelayBoard starter and ask it to explain the project without editing anything.

Useful command
claude --permission-mode plan

Work sequence

  1. Run the setup script for your platform and enter the generated relayboard-work directory.
  2. Start Claude Code in plan mode or explicitly request read-only exploration.
  3. Ask for the entry points, domain model, test command, and one uncertainty.
  4. Compare every claim with an inspected file or command output.

Record the checkpoint after you can identify one observation, one decision, one action Claude proposed, and one verification signal.

COMMON FAILURE MODES

Watch for these

  • Treating the conversation as the complete source of truth
  • Approving commands without understanding their scope
  • Equating a plausible answer with repository evidence
SAFETY + VERIFICATION

Pause before proceeding

Before approving an action, read the full command, resolve its target, and ask whether the result is reversible. Never widen permission merely to avoid repeated prompts.

ONE-SENTENCE TAKEAWAY

Trust the loop only to the degree that its context, authority, and verification are visible.
