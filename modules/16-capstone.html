Capstone: deliver a trusted repository change

Combine only the context, authority, extensions, and automation your outcome can justify.

PLAIN-LANGUAGE DEFINITION

The capstone is an end-to-end demonstration that a learner can frame, execute, verify, review, and hand off a real repository change with explicit trust boundaries and recoverable evidence.

Learn→Demonstration→Guided lab→Transfer→Evidence→Quiz
BY THE END

You will be able to—

  1. 01Deliver a repository change from issue to verified diff
  2. 02Use Claude Code features proportionately
  3. 03Defend the result with evidence, remaining risk, and a rollback path
KEY TERMS

Words to use precisely

Evidence packet
The linked specification, plan, diff, tests, reviews, and operational notes supporting acceptance.
Critical criterion
A safety or verification condition that cannot be offset by points elsewhere.
Handoff
A concise artifact enabling another engineer to review, continue, operate, or reverse the work.

01
Assignment

Add incident escalation without breaking trust

Implement an escalation policy for RelayBoard. An acknowledged P1 incident older than a configurable threshold becomes escalation-eligible. An operator may escalate it with a reason; viewers cannot. Repeated requests are idempotent. The API must preserve existing response shapes, emit an audit event, and expose enough structured evidence for operations.

You must investigate the repository, resolve ambiguity in a written spec, choose an implementation plan, configure only justified extensions, implement in bounded slices, and verify the combined behavior.

  • Do not expose secrets or use production services.
  • Do not bypass permissions.
  • Do not change unrelated public contracts.
  • Do not claim completion without red-capable tests and reviewed evidence.
02
Review

The evidence packet is the deliverable

A reviewer should be able to understand the problem, reproduce important checks, inspect the change surface, evaluate risk, and recover without reading the full Claude conversation.

Export the Engineering Evidence Log and add direct references to the issue, spec, plan, Git history, test output, security review, and rollback note. State remaining uncertainty rather than filling gaps with confidence.

  • Include the exact baseline and final test commands.
  • Separate automated evidence from manual inspection.
  • Record rejected approaches that affect future maintenance.
  • Name the human decision that accepts the remaining risk.
Example
npm test
npm run typecheck
git status --short
git diff --check
git diff <baseline>...HEAD

PRACTICAL FRAMEWORK

The TRUSTED handoff

Your reviewer should find each item without reconstructing the session.

  1. 01
    Task

    Approved outcome, scope, non-goals, and acceptance criteria.

  2. 02
    Risk

    Data, permissions, threat model, and critical decisions.

  3. 03
    Updates

    Change summary, architecture effects, and migrations.

  4. 04
    Signals

    Red-capable tests, broad suite, manual checks, and review.

  5. 05
    Exit

    Remaining uncertainty, owner decision, rollback, and follow-up.

WHY IT WORKS

The handoff connects scope, history, evidence, risk, recovery, and accountable human judgment.

TRY IT IN CLAUDE CODE

A reusable starting request

Adapt bracketed material to approved project information. Review proposed actions before granting authority.

Act as my capstone delivery partner for the RelayBoard escalation feature. Work from an approved specification. Keep a visible task plan, use the narrowest permissions, implement one bounded slice at a time, stop when evidence contradicts the plan, and require review before consequential actions. At completion, produce a TRUSTED handoff with direct evidence and remaining uncertainty.

GUIDED RELAYBOARD LAB

Deliver incident escalation

25–35 min

Scenario

Complete the assignment against a fresh learner branch and produce a reviewable evidence packet.

Useful command
npm test && npm run typecheck

Work sequence

  1. Create and approve the specification and risk assessment.
  2. Map the change surface and make a checkpointed plan.
  3. Implement domain, persistence/audit, and interface slices with tests.
  4. Run adversarial review, broader verification, and recovery rehearsal.
  5. Export the Evidence Log and complete the capstone rubric.

The capstone is complete only when all critical checklist items below are satisfied and the evidence packet lets another engineer reproduce the decision.

COMMON FAILURE MODES

Watch for these

  • Using every course feature whether or not the outcome needs it
  • Submitting transcript length instead of evidence
  • Allowing a polished feature to compensate for a critical security or verification gap
SAFETY + VERIFICATION

Pause before proceeding

Critical safety criteria are non-compensating. If authorization, secrets, destructive scope, verification, or recovery is unresolved, the capstone is not ready regardless of feature quality.
