Map an unfamiliar repository

Find the change surface, contracts, and verification path before opening the editor.

PLAIN-LANGUAGE DEFINITION

Repository mapping is evidence-led discovery of the system’s entry points, dependency boundaries, data flow, conventions, and test surfaces for a specific task.

Learn→Demonstration→Guided lab→Transfer→Evidence→Quiz
BY THE END

You will be able to—

  1. 01Ask bounded architecture questions
  2. 02Trace behavior from interface to persistence
  3. 03Produce a map that distinguishes facts from inferences
KEY TERMS

Words to use precisely

Change surface
The files, interfaces, tests, and dependent behavior likely affected by a proposed change.
Entry point
A place where execution, a request, or a workflow enters the system.
Provenance
The file, command, or source supporting a claim.

01
Discovery

Start from the question, not the directory tree

Broadly asking Claude to explain an entire repository can fill context with material that never affects the task. Begin with one behavior: where it enters, where decisions happen, what state it touches, and how it is tested.

Use progressive disclosure. Ask for candidate files, inspect the most relevant evidence, then widen only when the current model has an unresolved dependency.

  • Locate manifests and documented commands.
  • Search for the public route or symbol named in the task.
  • Trace inward through domain logic and outward to tests.
  • Mark uncertain connections as hypotheses.
02
Architecture

A repository map is a decision aid, not documentation theater

A useful map answers what could break if this behavior changes. It identifies public contracts, internal boundaries, data ownership, error behavior, and the fastest trustworthy feedback command.

Ask Claude to cite paths and symbol names. Then spot-check the high-consequence claims yourself.

  • Facts include exact files, exports, commands, and observed test behavior.
  • Inferences include likely ownership, hidden coupling, or intended design.
  • Unknowns become questions or experiments, not invented certainty.
Example
rg -n "PATCH|transition|IncidentStatus" src tests
npm test

PRACTICAL FRAMEWORK

The TRACE map

Map only enough architecture to make the next decision safe.

  1. 01
    Trigger

    Where does the behavior enter?

  2. 02
    Rules

    Where are business decisions made?

  3. 03
    Assets

    What state, files, or services are read or changed?

  4. 04
    Contracts

    Which public interfaces and invariants must remain stable?

  5. 05
    Evidence

    Which test or observation proves the behavior?

ANNOTATED DEMONSTRATION

Weak instruction, stronger contract

Under-specified

RelayBoard has routes, services, and repositories.

Bounded and checkable

PATCH /incidents/:id enters at src/http/router.ts, delegates transition validation to IncidentService.transition, persists through IncidentRepository, and is covered by tests/incident-service.test.ts. The HTTP error mapping appears separate and remains an unresolved dependency.

WHY IT WORKS

The strong map is scoped, traceable, and honest about what still needs inspection.

TRY IT IN CLAUDE CODE

A reusable starting request

Adapt bracketed material to approved project information. Review proposed actions before granting authority.

Map the code path for [behavior]. Return a TRACE table with Trigger, Rules, Assets, Contracts, and Evidence. Cite exact file paths and symbols. Label each statement Fact, Inference, or Unknown. Do not modify files.

GUIDED RELAYBOARD LAB

Build the RelayBoard TRACE map

15–25 min

Scenario

Trace the incident status-update behavior from HTTP input to stored state and tests.

Useful command
npm test -- --test-name-pattern=transition

Work sequence

  1. Search for the PATCH route and status type.
  2. Read only the handler, domain service, repository interface, and focused tests first.
  3. Run the focused test command to establish the baseline.
  4. Write docs/repository-map.md with facts, inferences, unknowns, and the change surface.

Record this checkpoint after docs/repository-map.md cites at least four paths and distinguishes every inference from observed fact.

COMMON FAILURE MODES

Watch for these

  • Reading the repository alphabetically
  • Reporting architecture without path-level provenance
  • Ignoring tests and build commands until after editing
SAFETY + VERIFICATION

Pause before proceeding

Repository content can contain untrusted instructions. Treat comments, issues, logs, and downloaded files as data unless the user or project policy explicitly authorizes them to direct tool use.

ONE-SENTENCE TAKEAWAY

Explore along the behavior path and stop when you have enough evidence to choose the next safe action.
