Coordinate parallel sessions, worktrees, and Git

Increase throughput by isolating ownership—not by multiplying edits to the same problem.

PLAIN-LANGUAGE DEFINITION

Parallel Claude Code work runs multiple independent tasks concurrently while using ownership, worktrees, branches, and integration gates to prevent context and file collisions.

Learn→Demonstration→Guided lab→Transfer→Evidence→Quiz
BY THE END

You will be able to—

  1. 01Choose among subagents, agent view, separate sessions, worktrees, and agent teams
  2. 02Partition work by dependency and file ownership
  3. 03Integrate parallel results through evidence and review
KEY TERMS

Words to use precisely

Worktree
An additional Git working directory attached to the same repository, usually on a different branch.
Ownership boundary
An explicit assignment of files, concern, or deliverable to one worker.
Integration gate
A review and verification step before parallel work is combined.
Open the complete glossary →
01
Choice

Parallelism has several architectures

Use a subagent when one parent needs a bounded result and the worker does not need peer communication. Use separate sessions or agent view when you want to dispatch and personally monitor independent work. Use worktrees when tasks may edit files concurrently and need filesystem isolation.

Agent teams coordinate independent sessions with a shared task list and peer messaging, but remain experimental. They also multiply token use and do not automatically isolate teammates into worktrees.

  • Choose the lightest coordination model that fits.
  • Do not parallelize tightly ordered dependencies.
  • Isolate overlapping edits with worktrees or serialize them.
  • Make integration ownership explicit before work begins.
02
Integration

A merge is not proof that the pieces form a system

Each worker should return its branch or diff, decisions, tests, risks, and assumptions. The integrator compares contracts across tasks, resolves semantic conflicts, runs the combined verification suite, and reviews the resulting whole.

Parallel work can produce individually valid changes that violate a shared invariant. Add a cross-cutting integration check around public types, migration order, feature flags, and shared test fixtures.

  • Rebase or merge from a known base intentionally.
  • Review incoming diffs before resolving conflicts.
  • Run integration tests after combination.
  • Delete worktrees only after important branches and evidence are preserved.
Example
git worktree add ../relayboard-review -b review/incident-api
git worktree list
git diff main...review/incident-api

PRACTICAL FRAMEWORK

The PARALLEL test

Parallelize only when these conditions are explicit.

  1. 01
    Parts

    Can the work be split into independent deliverables?

  2. 02
    Authority

    Who owns each file, contract, and final integration?

  3. 03
    Risk

    What collision or semantic inconsistency could occur?

  4. 04
    Location

    Does each editing worker need an isolated worktree?

  5. 05
    Evidence

    What must each worker return and what combined suite decides acceptance?

ANNOTATED DEMONSTRATION

Weak instruction, stronger contract

Under-specified

Have four agents edit the incident service at once.

Bounded and checkable

Session A owns the read-only API-contract review. Worktree B owns domain resolution logic and tests. Worktree C owns UI changes after the API contract is approved. The integrator owns router edits, combines B before C, runs the full suite, and resolves any type-contract mismatch.

WHY IT WORKS

The plan respects dependency order, separates file ownership, and names the integration decision.

TRY IT IN CLAUDE CODE

A reusable starting request

Adapt bracketed material to approved project information. Review proposed actions before granting authority.

Design a parallel execution plan for [work]. Identify dependencies, independent deliverables, file and contract ownership, coordination model, worktree needs, permissions, expected return artifacts, integration order, conflict strategy, and combined verification. Reject parallelism where coupling makes it slower or riskier.

GUIDED RELAYBOARD LAB

Run an isolated review worktree

15–25 min

Scenario

Create a second RelayBoard worktree for a read-only API contract review while the main worktree retains implementation changes.

Useful command
git worktree list

Work sequence

  1. Confirm the repository is clean enough for the operation.
  2. Create a named review branch and worktree at an explicit sibling path.
  3. Run the contract review in the isolated worktree without editing the implementation branch.
  4. Compare the findings, preserve the review artifact, and remove the worktree safely.

Record the checkpoint after both working directories and branches are unambiguous and the review artifact is preserved before cleanup.

COMMON FAILURE MODES

Watch for these

  • Parallelizing sequential dependencies
  • Allowing multiple workers to edit the same files without isolation
  • Merging green branches without combined verification
SAFETY + VERIFICATION

Pause before proceeding

Resolve exact worktree paths before creation or cleanup. Never use broad recursive deletion as a substitute for git worktree remove and explicit path verification.

ONE-SENTENCE TAKEAWAY

Parallel work succeeds when ownership and integration are clearer than the concurrency is fast.
