Turn ambiguity into specifications and plans

Make the problem reviewable before asking Claude to make it real.

PLAIN-LANGUAGE DEFINITION

A specification states observable behavior, constraints, edge cases, and acceptance evidence; a plan sequences the repository changes needed to satisfy that contract.

Learn→Demonstration→Guided lab→Transfer→Evidence→Quiz
BY THE END

You will be able to—

  1. 01Separate requirements from implementation choices
  2. 02Use interviews to expose consequential ambiguity
  3. 03Create plans with checkpoints and rollback boundaries
KEY TERMS

Words to use precisely

Acceptance criterion
An observable condition that must be true for the work to be accepted.
Invariant
A condition that must remain true before and after the change.
Decision point
A place where different answers materially change scope, design, risk, or verification.

01
Specification

Let Claude interview the problem before it invents the solution

Large changes fail early when apparently simple words hide policy decisions. Ask Claude to surface ambiguities about users, states, failure modes, compatibility, security, and operational behavior.

A good interview does not ask the user for facts that the repository can answer. It investigates code first, then asks only decisions the evidence cannot settle.

  • Write acceptance criteria in behavior language.
  • List non-goals to constrain enthusiasm.
  • Name data and API compatibility requirements.
  • Record who owns unresolved product decisions.
02
Planning

A plan should be falsifiable at every stage

Useful plans name the files or boundaries likely to change, but they remain open to correction when exploration reveals a different structure. Each step should end in an inspection, test, or reviewable artifact.

Separate exploration from mutation. For high-uncertainty work, create the spec in one clean session and execute it in another so failed approaches do not become part of the implementation context.

  • Sequence prerequisites before dependents.
  • Keep one concern per step.
  • Add an explicit stop if evidence contradicts the plan.
  • Place destructive or externally visible actions behind approval.
Example
claude --permission-mode plan
# after SPEC.md is approved
claude "Implement @SPEC.md one checkpoint at a time"

PRACTICAL FRAMEWORK

SPEC before steps

Make these five dimensions explicit before implementation.

  1. 01
    Success

    What can an observer see when the change works?

  2. 02
    Policy

    Which business rules and invariants govern it?

  3. 03
    Edges

    What invalid, concurrent, empty, or degraded cases matter?

  4. 04
    Constraints

    What must not change, and what authority is unavailable?

  5. 05
    Checks

    Which automated and manual evidence will decide acceptance?

ANNOTATED DEMONSTRATION

Weak instruction, stronger contract

Under-specified

Add incident resolution.

Bounded and checkable

An operator may move an acknowledged incident to resolved only when resolutionSummary is 20–500 characters. Anonymous and viewer roles receive 403. Invalid transitions return the existing 409 shape. The list endpoint remains backward compatible. Unit tests cover allowed, forbidden, invalid-state, and missing-summary cases; the browser flow is manually checked.

WHY IT WORKS

Observable behavior and preserved contracts leave implementation flexibility without leaving policy ambiguous.

TRY IT IN CLAUDE CODE

A reusable starting request

Adapt bracketed material to approved project information. Review proposed actions before granting authority.

We need to change [behavior]. Inspect the repository for facts first, then interview me only about decisions the code cannot answer. Cover user outcome, states, edge cases, compatibility, security, observability, non-goals, and acceptance evidence. When settled, write SPEC.md and a checkpointed implementation plan. Do not implement yet.

GUIDED RELAYBOARD LAB

Specify incident resolution

25–35 min

Scenario

RelayBoard needs a safe transition from acknowledged to resolved with a required resolution summary.

Useful command
claude --permission-mode plan

Work sequence

  1. Ask Claude to inspect current states, role checks, errors, and tests.
  2. Answer product decisions; refuse questions the repository can answer.
  3. Write docs/resolution-spec.md with scenarios and non-goals.
  4. Have Claude critique the spec for ambiguity and missing verification.

Record this checkpoint when another learner could implement the change without inventing policy and every criterion has a proposed check.

COMMON FAILURE MODES

Watch for these

  • Writing implementation steps as product requirements
  • Asking dozens of low-value questions before inspecting the code
  • Using ‘works correctly’ as an acceptance criterion
SAFETY + VERIFICATION

Pause before proceeding

Do not let a specification silently grant access, broaden data collection, or authorize external actions. Those are explicit owner decisions.

ONE-SENTENCE TAKEAWAY

A strong specification removes policy ambiguity; a strong plan makes each implementation claim testable.
