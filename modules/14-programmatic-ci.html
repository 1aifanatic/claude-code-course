Run Claude Code programmatically and in CI

Convert an interactive workflow into bounded automation with machine-readable outcomes.

PLAIN-LANGUAGE DEFINITION

Programmatic mode runs Claude Code non-interactively through claude -p or the Agent SDK, using explicit inputs, tool limits, output formats, turn bounds, and process exit behavior.

Learn→Demonstration→Guided lab→Transfer→Evidence→Quiz
BY THE END

You will be able to—

  1. 01Design a non-interactive task contract
  2. 02Use structured output and bounded tools
  3. 03Place Claude in CI without granting repository or secret authority casually
KEY TERMS

Words to use precisely

Non-interactive mode
A single-run mode invoked with -p or --print that returns output and exits.
Structured output
Machine-readable JSON or schema-constrained data designed for downstream automation.
Turn limit
A bound on how many agentic iterations a programmatic run may take.

01
Automation

A scheduled or CI agent cannot interview its way out of ambiguity

Non-interactive tasks need explicit success, available evidence, allowed tools, output contract, failure behavior, and cost or turn bounds. If a missing decision would change the result, fail visibly rather than guess.

Use --bare when you intentionally want minimal startup configuration; otherwise remember that project and user extensions may load into the run. Structured output lets downstream code validate shape, but it does not prove factual correctness.

  • Provide a narrow, deterministic input set.
  • Use --allowedTools and --disallowedTools.
  • Set --max-turns and a timeout in the caller.
  • Return a nonzero process result or explicit status on blocked work.
02
CI security

Repository events are untrusted input with credentials nearby

Pull-request text and changed files can contain prompt injection. CI tokens may write comments, branches, releases, or infrastructure. Keep default permissions read-only, separate analysis from mutation, protect secrets from forked contributions, and require human approval before high-impact actions.

Prefer reporting a structured review artifact over automatically committing fixes. Add concurrency controls, rate or cost limits, logs, and a kill switch.

  • Pin action and dependency versions.
  • Minimize token and repository scopes.
  • Do not expose secrets to untrusted forks.
  • Separate advisory checks from write-capable workflows.
Example
claude -p "Review the current diff for API contract regressions. Return JSON only." \
  --allowedTools "Bash(git diff *)" "Read" "Grep" \
  --disallowedTools "Edit" "Write" \
  --max-turns 6 --output-format json

PRACTICAL FRAMEWORK

The BATCH contract

Automation should terminate predictably and leave evidence.

  1. 01
    Boundary

    Which input, repository state, and external systems are in scope?

  2. 02
    Authority

    Which tools, token scopes, and writes are allowed?

  3. 03
    Termination

    What turn, time, cost, and retry limits apply?

  4. 04
    Contract

    What output schema and exit behavior do callers consume?

  5. 05
    Human gate

    Which consequential result requires review before action?

ANNOTATED DEMONSTRATION

Weak instruction, stronger contract

Under-specified

Run Claude on every pull request with a write token and let it fix anything.

Bounded and checkable

On trusted pull requests, run a read-only contract-review prompt against the diff with six turns, a five-minute timeout, explicit Read/Grep/git diff tools, JSON output validated against a schema, and no secrets. Publish the report as a check; a maintainer chooses whether to invoke a separate fix workflow.

WHY IT WORKS

The automation has bounded input, authority, termination, output, and escalation.

TRY IT IN CLAUDE CODE

A reusable starting request

Adapt bracketed material to approved project information. Review proposed actions before granting authority.

Convert this interactive Claude Code workflow into a non-interactive automation. Define trusted and untrusted inputs, prerequisites, prompt, allowed and denied tools, startup configuration, output schema, exit codes, time and turn limits, retries, cost visibility, logs, secret handling, and the human approval gate. Include a dry-run mode.

GUIDED RELAYBOARD LAB

Build the read-only contract reviewer

25–35 min

Scenario

Add a local npm script that asks Claude to review a prepared diff and return a bounded JSON report without editing files.

Useful command
npm run review:contract -- --dry-run

Work sequence

  1. Write the output schema and failure states first.
  2. Create scripts/review-contract.mjs that invokes claude -p with explicit tools and max turns.
  3. Add a dry-run that prints the command without execution.
  4. Test valid output, malformed output, timeout, missing Claude, and an injected instruction inside the diff.

Record this checkpoint when the dry-run reveals every authority boundary and automated tests reject malformed output and prompt-injection instructions.

COMMON FAILURE MODES

Watch for these

  • Automating a prompt that still depends on interactive clarification
  • Granting write authority to an advisory review job
  • Treating valid JSON as proof that the underlying claims are true
SAFETY + VERIFICATION

Pause before proceeding

A CI run combines untrusted repository content with privileged infrastructure. Use read-only defaults, explicit trust boundaries, protected secrets, and a separate reviewed mutation path.

ONE-SENTENCE TAKEAWAY

Programmatic Claude Code is production automation: bound its inputs, authority, termination, outputs, and escalation.
